# Daily Worklog

## 目的

その日の作業内容を `worklog/YYYY-MM-DD.md` に残し、次回の再開を速くする。

## 初学者向け（このスキルで何をするか）

**ワークログ（日報）**は、その日どこまで進めたかを **短いメモ** にしたものです。日記のように感情や細部の手順を全部書く必要はなく、**あとから自分（やチーム）が続きを思い出せる**ことが目的です。

**Cursor のスキル**は「こういう依頼が来たら、このルールに従って書く」という説明書です。ユーザーが「日報」「work log」「今日のまとめ」などと頼んだとき、エージェントがこのファイルのルールに沿って `worklog/` 以下に Markdown を作ります。スキル自体が自動で日報を書き続けるわけではなく、**依頼したタイミングでまとめを出す**ための型です。

**`worklog/` ディレクトリ**はリポジトリ内のフォルダです。まだ無ければ、その日のファイルを作るときに一緒に用意すればよいです。**ファイル名は日付**（`2026-05-09.md` のように）にすると、あとから日付で探しやすいです。

**テンプレートの各見出しの意味**の目安です。

| 見出し | 意味（ざっくり） |
|--------|------------------|
| 今日やったこと | 実装・調査・ミーティングなど、終わったこと・進んだこと |
| 反映状況 | コードが **どの環境・ブランチに載ったか**（PR マージ済みか、stg だけか など） |
| 未完・課題 | 未解決のバグ、決めていない設計、次に調べること |
| 明日の最初の1手 | 翌日、**最初に手を付ける1つだけ**（迷いを減らすため） |

最初は項目をすべて埋めなくてもよいです。慣れたら「反映状況」と「明日の最初の1手」を必ず書くと、再開が楽になります。

## 保存先ルール

- ディレクトリ: `worklog/`
- ファイル名: `YYYY-MM-DD.md`（例: `2026-05-08.md`）
- 1日1ファイル。追記方式でも上書き整理でもよいが、最終的に1ファイルへ集約する。

## 手順

1. 今日の日付を確認し、対象ファイル `worklog/YYYY-MM-DD.md` を決める。
2. その日の作業ログ（コミット、PR、実行結果、障害対応）を要約する。
3. 以下テンプレートに沿って Markdown を作成/更新する。
4. 未確定事項は「未完・課題」に明示し、次のアクションを1つだけ書く。

## テンプレート

```markdown
# YYYY-MM-DD Worklog

## 今日やったこと
- 

## 反映状況（PR / main / stg / prod）
- 

## 未完・課題
- 

## 明日の最初の1手
- 
```

## ガイドライン

- 事実ベースで短く書く（長文説明より箇条書き）。
- PR番号・タグ・環境名は具体的に書く。
- 「やったこと」と「反映されたこと」を分ける。
- 「明日の最初の1手」は必ず1つに絞る。
